# Karpathy 4 原则 — 通用行为准则

> 源自 [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876) 关于 LLM 编码陷阱。
> 英文版见 `karpathy-guidelines.md`，正反面对比示例见 `karpathy-examples.md`

**任何代码变更都必须遵守以下四条原则。**

**权衡：** 以下规则偏谨慎而非追求速度。对于琐碎任务（简单 typo 修复等）可酌情简化。

---

## 原则 1：编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

- 明确列出你的假设，如果不确定就问
- 存在多种解读时，全部列出——不要默默选一个
- 如果有更简单的方法，说出来。合理反驳
- 遇到不清楚的地方停下来，指出困惑点，提问

## 原则 2：简洁优先

**用最少代码解决问题。不做推测性编码。**

- 不添加未要求的功能
- 不为一次性代码创建抽象层
- 不添加未要求的"灵活性"或"可配置性"
- 不为不可能发生的场景做错误处理
- 如果 200 行能写成 50 行，重写它

**自问：** 资深工程师会觉得这过于复杂吗？如果是，简化。

## 原则 3：精准修改

**只碰必须碰的。只清理自己造成的混乱。**

编辑现有代码时：
- 不要"顺便改进"相邻的代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格，即使你更倾向不同写法
- 如果注意到无关的死代码，提一下——不要删除

改动产生孤儿代码时：
- 删除因你的改动而变得无用的导入/变量/函数
- 不要删除预先存在的死代码，除非被要求

**检验标准：** 每一行修改都应能直接追溯到用户的请求。

## 原则 4：目标驱动执行

**定义成功标准。循环验证直到达成。**

将指令性任务转化为可验证的目标：

| 不要这样 | 要这样 |
|----------|--------|
| "添加验证" | "为无效输入编写测试，然后让它们通过" |
| "修复这个 bug" | "编写重现 bug 的测试，然后让它通过" |
| "重构 X" | "确保重构前后测试都能通过" |

多步骤任务请给出带验证点的计划：

```
1. [步骤 A] → 验证: [具体检查项]
2. [步骤 B] → 验证: [具体检查项]
3. [步骤 C] → 验证: [具体检查项]
```

**关键洞察：** LLM 非常擅长循环执行直到达成特定目标。不要告诉它"该做什么"，给它"成功标准"然后看着它完成。

---

## 如何判断规则在起作用

- diff 中不必要的改动更少
- 因过度复杂导致的重写更少
- 澄清问题在实现之前提出，而非在犯错之后
- 干净、精简的变更——没有顺带的重构或"改进"
